# Правила для ИИ-кодера этого репозитория

Проект: однофайловые Python-модули для Telegram-юзербота Heroku
(`Heroku-userbot/Heroku`, ветка `master`; форк — заводится и на Hikka).
В `bot/` — отдельный Gemini-бот для домашнего сервера. Установка:
`.addrepo https://github.com/xmogdemaybe/modulesheroku/raw/main`, затем
`.dlmod <имя>`; raw-ссылка с ветки PR позволяет тестить модуль до мержа.

## Как работать

- Один модуль = один `.py` в корне; имя файла — имя для `.dlmod`. В подпапки
  модули не переносить: raw-установка сломается.
- Шапка модуля — русский комментарий: идея, поведение, список команд
  (образец — `badapple.py`).
- Импорты относительные (`from .. import loader, utils`): лоадер грузит
  модуль как пакет, на абсолютные не переделывать.
- API Heroku сверять по апстрим-клону `C:\Users\User\Documents\refs\Heroku`
  (`heroku/loader.py`, `dispatcher.py`, `database.py`, `types.py`), а не по
  памяти.
- Команды регистрировать через `@loader.command(ru_doc=..., en_doc=...)`;
  модуль — класс `loader.Module` со `strings = {"name": ...}`.
- БД — JSON: `utils.is_serializable` отсекает сырые байты, бинарное хранить
  в base64.
- Вотчеры запускаются параллельно через `asyncio.ensure_future`: общее
  состояние защищать `asyncio.Lock`, стейт обновлять ДО `await`.
- `herokutl` — форк Telethon: при `FloodWaitError` спать ровно сколько
  просит Telegram, курсор и счётчики на паузе не двигать.

## Проверка

- Минимум после любой правки — `python -m py_compile <модуль>.py`.
- Модуль с логикой получает смоук-тест со стабами heroku/herokutl (образец —
  `smoke_badapple.py`); новое поведение закрывается тестом до коммита.
- Смоук-тест включает режим `--mutate`: сломать поведение и убедиться, что
  падает ровно предсказанный набор тестов. Зелёный прогон без мутации
  ничего не доказывает.
- Полный рантайм — только на боте владельца: `.dlmod` по raw-ссылке ветки
  PR, мерж после его теста и отмашки.
- Без прогона «проверено» не писать; пустой вывод скана — провал проверки,
  а не чистый результат.

## Мелкая гигиена правок

- Диф минимальный: соседний код не переотступать, попутный рефакторинг не
  вкатывать.
- Файлы под две тысячи строк (`triggerchanger.py`, `betonomeshalka.py`,
  `bot/`) целиком не читать: сначала `rg` по символу, потом кусок вокруг
  находки.
- Комментарии по-русски, в одну строку, только там, где без них неочевидна
  ловушка.

## Git: шлюз разрешений

- Репо публичный, основная ветка `main`. Читать (`status`, `log`, `diff`,
  `show`, `fetch`) — свободно; мутирующее — только по явной отмашке на
  конкретный шаг, без цепочки «коммит + пуш».
- Задача = отдельная ветка + PR (`gh pr create`). Прямые коммиты в `main`
  запрещены; исключение «коммитить прямо в main» из Rin сюда не
  распространяется.
- Фикс зависит от открытого PR — стек PR поверх верхней ветки
  (`--base <верхняя_ветка>`); порядок слития стека писать владельцу явно:
  мерж зависимого PR вольёт код в базовую ветку, а не в `main`.
- Перед пушем — `fetch`: владелец мог коммитить с веба GitHub. Интегрировать
  rebase'ом поверх его коммитов, сохраняя их; force-push без прямого приказа
  запрещён.
- Identity через `-c` (глобальный конфиг не задан), в том числе при ребейзе:
  `git -c user.name="xmogdemaybe" -c user.email="xmogdelegenda@gmail.com" commit ...`
- Слияние: `gh pr merge N --merge --delete-branch`; в стеке сначала
  переставить базу зависимых PR, потом сливать базовую ветку — иначе
  зависимые закроются автоматически.

## Формат сообщения коммита

- Префикс обязателен и отражает суть результата: `[+]` — новая возможность,
  `[*]` — багфикс или смена поведения, `[-]` — что-то убрано, `[=]` —
  документация, тесты и рутина без смены поведения.
- Одна короткая человеческая строка: что стало видно или что перестало
  ломаться. Без стеков вызовов, без перечисления файлов, без пересказа диффа.
- Без `Co-Authored-By` и любых подписей ИИ.
- «fix», «update», «правки по ревью» и строка длиннее одной фразы — не
  сообщение коммита, а его отсутствие. Такие переписывать до отправки.

## Чего не трогать

- `README.md` — территория владельца: без прямого приказа не менять,
  авторские формулировки не «причёсывать». `LICENSE` и `full.txt` не трогать.
- Ключи, токены и личные конфиги в git не попадают: бот из `bot/` работает
  на домашнем сервере со своими ключами.
- Рабочие дампы и временные файлы не коммитить; смоук-тесты — полноценные
  файлы репозитория, а не одноразовые скрипты.
